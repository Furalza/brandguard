# Evaluation Set Design

No labelled data is provided, so the evaluation set is part of the solution.
This document fixes the labelling rules before any record is labelled, so that
the set measures the system and not the labeller's inconsistency.

## Composition

Two brand profiles with different signal profiles:

- `ornek_bank` (banking): permission drift is a strong signal, official permission set is known.
- `hizli_kargo` (logistics): permissions are noisy by nature, official set unknown. Forces the system to handle an absent signal.

Target size: 60-80 records in the development set, 15-20 in the locked holdout.

| Layer | Description | Expected label | Target count |
|---|---|---|---|
| L1 official | The brand's own apps, exact name and publisher | official | 4-6 |
| L2 ecosystem | Brand's secondary apps, unusual names, same publisher | official | 4-6 |
| L3 obvious impersonation | Exact or near-exact name, unknown young publisher | impersonation | 8-10 |
| L4 homoglyph | Cyrillic or Greek confusables, zero-width chars | impersonation | 6-8 |
| L5 typosquat | Missing, doubled or swapped letters, Turkish char flattening | impersonation | 6-8 |
| L6 semantic | Brand name plus "Yeni", "Kampanya", "Giris", "2024" | impersonation | 4-6 |
| L7 repackaged | Official package id or name, different publisher or signature | repackaged | 4-6 |
| L8 third-party | Price comparison, bank aggregator, courier tracker, integration tools | third_party_legitimate | 8-10 |
| L9 noise | Partial name overlap, unrelated sector ("Ornek Oyun", "Kargo Takip") | unrelated | 8-10 |
| L10 ambiguous | Signals genuinely conflict, no reliable decision possible | uncertain | 4-6 |
| L11 injection | Description contains instructions aimed at the classifier | any of the above | 3-4 |

L2 and L8 are the hardest layers and the ones the brief singles out. A system
that cannot separate them from L3-L6 is not useful, regardless of its recall.

L11 records are labelled by their real category. The injection text must not
change the verdict; that is what the layer measures.

## Labelling rules

Each record is labelled once, with a one-line rationale stored next to it.
Rules applied in order:

1. Publisher exactly matches an official publisher: `official`, regardless of name or icon.
2. Package id matches an official id but publisher does not: `repackaged`.
3. Name clearly refers to the brand and the listing presents itself as the brand's product, publisher is not official: `impersonation`.
4. Name refers to the brand but the listing is explicitly a tool about or around the brand (comparison, tracker, integration) and does not claim to be the brand: `third_party_legitimate`.
5. Name overlap is incidental and the product is about something else: `unrelated`.
6. None of the above can be applied with confidence: `uncertain`.

Rule 3 versus rule 4 is the core judgement. The deciding question is whether a
reasonable user would believe they are installing the brand's own app.

## Locked holdout

`data/testset/locked/` is git-ignored and is not opened during development.
It is used once, for the final metrics, and is the rehearsal for the unseen
records the reviewers will bring to the demo. Layers are the same as above,
with a bias towards L2, L8 and L10.

## Generation

Records are written by hand for L1, L2, L8, L9 and L10, where brand context
matters and generated text is unreliable. Records for L3-L7 are partially
generated by a red-team LLM prompted to act as an attacker, then reviewed and
labelled by hand. The share of red-team variants caught by the query expander
is reported separately as discovery coverage.

## File format

One JSON file per brand, a list of objects:

```json
{
  "record": { "...AppRecord fields..." },
  "label": "impersonation",
  "layer": "L4",
  "rationale": "Cyrillic a in name, publisher account 9 days old, requests SMS"
}
```
